# Simulation reference

For physics, circuit, component, and board-format changes. See [UI/lifecycle](ui-lifecycle.md) for session ownership and [rendering](rendering.md) for visual state. Planned changes belong in [todos.md](todos.md).

## Ownership and tick model

* `src/simulation/world.ts` owns the board. `cell-storage.ts` bundles the dense per-cell typed arrays (tile kinds, stable IDs, orientations, handedness, charges, furnace state, weld edges) with whole-board and whole-cell clear/copy primitives, so a new per-cell field is added there once; `World` adds sparse per-ID component state and every invariant on top. Empty cells have ID 0. Geometry and visual revisions are separate.
* `simulation.ts` coordinates observation, intent resolution, and commit. Components observe the start-of-tick state, not another component's newly committed action. Circuit propagation resolves an entire welded network in one phase; gates use previously observed inputs. Piston substeps are the geometry-only exception: they reuse the tick's resolved charges while observing earlier piston strokes.
* `world-runtime.ts` retains one `WorldRuntime` per board identity. Machine resolvers, the observer welded-body index, ordinary-motion scratch, and circuit output/control buffers allocate on first use and remain cached for that runtime's lifetime, including across reset. `world-features.ts` centrally maintains feature counts and row-major bitset indices through tile-kind mutations. Each phase checks current features so edits or earlier commits can activate previously absent machinery. Circuit source reads access machine scratch only for the corresponding source kind.
* `welded-body-index.ts` retains start-of-tick body membership, bounds, and exact structural matching. It and `motion-workspace.ts` cache welded roots by geometry revision and magic-link topology revision. `magic-link.ts` shares lazy per-world mechanical link adjacency across observers, ordinary motion, rotators, and piston closure; two sparse directional sweeps find nearest opposing links. Magnetic contacts and body movement properties are recomputed; post-weld motion never reuses stale start-of-tick geometry. `piston-resolver.ts` owns reusable stroke proposals and transient weld/contact traversals for its substeps.
* Magnetic constraint and gravity-transfer buffers inside `MotionWorkspace` allocate only on the first contact between distinct welded bodies, not merely when a magnet exists. Storage remains cached across removal/reset; each ordinary-motion pass starts with zero active constraints, and the first contact resets the head table. Contact-free passes neither clear nor traverse retained buffers, and reuse gravity's welded body membership/properties directly for driven motion. With active contacts, gravity movement is transferred back to the separate welded drive bodies and their properties are rebuilt, including levitation beams.
* Floating-body weight-propagation scratch inside `MotionWorkspace` allocates only when gravity first encounters floating tiles. It remains cached across removal/reset and is cleared before every active weight-propagation pass; ordinary boards allocate none of it.
* Ordinary motion records gravity destinations as byte-per-cell occupancy flags: driven movement needs to know whether gravity reserved a cell, not which body owns it. Clear and rebuild these flags on every driven-resolution pass, including powered reservation probes.
* Ordinary-motion horizontal and vertical displacement buffers use signed bytes: each axis is always -1, 0, or +1, independently of board size or total driving force. `World.moveBodies` also accepts 16-bit displacement buffers for wider translations; body roots and force sums remain 32-bit.
* Equal-priority competing intents jam. Resolve complete dependencies before moving any body; do not let iteration order pick winners. World boundaries are solid.

Component frames reflect local left/right before applying orientation. `TileDefinition.usesMirroring` marks conveyors, selectors, ROMs, lookup runes, assemblers, laser splitters, and rotators; `mirroringForKind` normalizes symmetric kinds to false. Handedness is independent of orientation support: conveyors have handedness without a facing direction. `World.place` accepts handedness after orientation, and `mirroredAt`/`mirroredAtIndex` expose it. `orientedDirection` and `orientedSides` resolve local semantics for circuits, welds, and machines. One reflected axis toggles handedness; two cancel; rotations retain it. Cell copies, movement, reset, nested boards, duplication, and queued assembler products preserve this state. Handedness changes invalidate geometry-dependent circuit topology.

Each tick collects intents throughout the root/nested-board tree, resolves circuits forest-wide, then commits the remaining phases in each board, children before parents. This lets duplication copy fully advanced inner contents. Preserve the explicit phase order in `simulation.ts`: circuit observations use old welds, whereas motion uses committed weld changes. Furnace/delivery/duplication changes can invalidate later machine claims; resolvers recheck the relevant IDs, kinds, and destinations before committing.

## Motion and machines

| System | Current contract / extension point |
| --- | --- |
| Gravity | Eligible bodies move at most one cell per tick. Straight-down movement outranks parity-selected diagonal sand movement and conveyor motion. Unsupported touching bodies resolve complete downward dependency chains. Platforms are fixed; sand is not weldable. |
| Fragile glass | `TileDefinition.fragile` marks glass. Unwelded glass breaks on the first tick without an accepted gravity fall after dropping more than one cell; resting glass and separate one-cell drops are safe. Any weld during ordinary motion protects it and clears fall history. Machinery-driven movement does not add fall distance. Landing tiles stay solid through movement resolution/commit, then break together before rotators and pistons run. Sparse per-ID `fragile` state saturates `fallDistance` at 2 and follows cloning/reset, transforms, duplication, and nested boards. Scene component entries validate 0–2 and omit zero; absent entries start at zero. Furnace-produced glass initializes the same state. Destruction records a render-only shatter effect, shared with drills and broken fasteners. |
| Floatstone | Suppresses gravity for its whole welded body without anchoring it. Independent, successfully falling bodies above activate downward movement through movable contact chains; bodies supported elsewhere exert no downward push. Pistons, conveyors (including upward forces), and rotators can move it. A welded platform still anchors it. Tile metadata separates `affectedByGravity` from optional `immovable`; ordinary motion only runs the weight-activation pass when floating tiles exist. |
| Levitation projectors | Suppress gravity for every body intersecting the forward ray unless the previous-tick isolated rear input is -1; zero, +1, and disconnected inputs enable the beam. Rear control accepts welded links and virtual array ports, with no circuit output. Disable commands are transient stable-ID observations cleared each tick, not serialized state. Rays start one cell ahead and pass through occupied cells/gaps until the front face of the first oppositely facing levitation projector (even disabled) or the local board boundary. Same-facing and perpendicular projectors do not stop rays. The terminating projector is excluded, so facing pairs do not hold each other aloft. `MotionWorkspace` applies the ray to magnetic gravity groups and again to welded drive groups, allowing upward conveyor movement without anchoring targets. Independent falling weight can still push them; platforms and sliders retain their restrictions. Rays observe pre-motion geometry on each ordinary motion pass, so entering/leaving a ray changes gravity on the next pass. The projector itself falls normally unless its body is supported or intersects a beam. Orientation is the only component configuration; cloning, transforms, duplication, and scene persistence use ordinary directional-tile paths. Nested boards project locally, never through array ports. |
| Sliders | Restrict their whole welded body's translation to the facing axis, in either direction. Up/down rails permit gravity; left/right rails block all vertical translation, including falling weight. Perpendicular welded rails block both axes. Ordinary gravity/magnetic groups aggregate blocked-axis bits; conveyor forces/contact chains and piston pushes, pulls, and recoil reject any translation crossing a locked axis. Rotator turns remain allowed under normal collision rules and rotate the permitted axis for subsequent motion. Orientation is the only state, so normal cloning, transforms, duplication, and scene persistence apply. |
| Magic links | Each link targets the first oppositely facing magic link ahead, skipping gaps, ordinary blocks, and other orientations. Every directed target relation adds an undirected mechanical edge, including nonreciprocal incoming links; their welded bodies merge transitively for support, motion constraints, pushing/pulling, rotation, matching, consumption, and duplication. Rays occupy no cells, carry no charge, and stay within the local board. Isolated rear previous-tick -1 disables every edge involving that endpoint; 0/+1/disconnected enables it, including virtual array ports. A disabled opposing link stops the search without connecting. Controls are sampled before body observers and frozen by stable ID through the tick; geometry changes rebuild links for later motion phases/piston rounds. Controls are transient, not serialized state. |
| Fasteners | Hold their welded body aloft like floatstone, including surviving downward pushes from independent falling weight. Successful conveyor/thruster movement, piston pushes/pulls/recoil, and rotator turns destroy every carried fastener and its welds; blocked or competing intents leave it intact. Fasteners remain solid through collision resolution and piston head-weld transitions, then break before the next motion phase. Released pieces obey gravity on the next ordinary motion pass. A sparse feature index and reusable destination list avoid scanning unrelated tiles for breakage. |
| Magnets and conveyors | Magnetic contacts group bodies against gravity, couple conveyor movement along the contact normal, and permit tangential sliding. Belts apply tangential forces to unwelded neighbors and opposite reactions to themselves. +1 spins clockwise and -1 counterclockwise; mirrored belts reverse both directions. Unsupported bodies fall first; belts cannot lift gravity-affected bodies. Supported movement resolves force sums, pushing chains, fixed blockers, and destination jams. |
| Thrusters | Suppress gravity for their welded body and apply constant forward force without charge. Share conveyor force sums, one-cell driven movement, contact-chain pushing, magnetic coupling, slider restrictions, and collision jams. Opposing forces on the same body cancel; incompatible separate-body moves jam. Powered chains take priority over gravity, including lifting unwelded loads and reserving destinations before falling bodies. Successful driven movement breaks carried fasteners. Orientation is the only state and follows ordinary transforms, duplication, and scene/nested-board persistence. Ordinary motion runs on thruster-only boards even without gravity-affected tiles. |
| Controlled thrusters | Four isolated inputs read previous-tick charges through welded links or virtual array ports. Exactly one +1 input applies force toward that side; zero/negative inputs do nothing and multiple positive inputs jam that thruster without anchoring the body. Suppress gravity even while idle and share ordinary thruster force sums, pushing, and collision rules. Circuit observation records transient stable-ID commands in the motion workspace, cleared before every tick; production cannot inherit a removed tile's command. No serialized component state or orientation is needed. |
| Force projectors | Previous-tick isolated rear +1 pushes the first occupied forward-ray target away; -1 pulls toward the projector; zero/disconnected input is idle. Rays stop at any tile, including glass and fixed terrain, and at the local board boundary. A target in the projector's own welded body blocks the ray without receiving force. Commands capture source/target IDs before production and recheck them before ordinary motion; removed targets are not replaced by farther targets until the next tick. Forces share conveyor/thruster sums, contact-chain pushing, magnetic coupling, slider restrictions, priority over gravity, and fastener breakage. Can lift ordinary gravity-affected targets; idle targets resume normal gravity. No recoil or gravity suppression for the projector itself. Orientation is the only persistent state; virtual rear array inputs and ordinary scene/transform/duplication paths apply. |
| Pistons | Positive charge prefers extension and forward pushing, then base recoil/rear pushing if blocked; a boundary can brace recoil. Negative charge retracts and pulls only a head-welded body. Neutral holds. Extended base and arm have separate IDs; head welds follow the arm while other welds/ports remain with the base. |
| Rotators | Rear +1/-1 turns a forward/side grip clockwise/counterclockwise, reversed for mirrored rotators, never toward the rear. A cell-center quarter-circle supercover recursively collects swept bodies and enclosed loose contents. If geometry blocks the gripped body's turn, try rotating the rotator's own body oppositely around its cell, leaving the grip's world direction/body stationary. Both proposals obey fixed-terrain, boundary, and stationary-body capture restrictions. Only the chosen proposal enters conflict resolution; competing feasible turns jam without trying reaction, and reaction claims its stationary grip against other turns. Turns preserve IDs/handedness and transform orientations, welds, crossing axes, and oriented state. |
| Welders/splitters | Operate on the two transverse edges of the cell ahead. Shared side -1 disables; isolated rear output pulses on a change. Opposing operations on one edge jam. Changes commit after circuit resolution and before motion. |
| Laser splitters | Cut the local-left edge of every forward cell to the board boundary, starting one cell ahead; mirrored splitters cut local-right instead. Pass through tiles and gaps without destroying tiles. Share ordinary splitter side-disable/rear-change-pulse semantics and per-edge welder conflicts; overlapping beams may both pulse for the same successful cut. |
| Furnaces | Transform sand to glass in four active ticks, ore to iron in six, or copper ore to copper in six while wood touches the ore orthogonally. Shared side -1 or missing required neighbors pauses progress; target-ID changes reset it. The isolated rear output is +1 on each active baking tick, including completion, and 0 while paused or without a recipe. Welded side ports link adjacent furnaces into one control network. Recipes live in `furnace.ts`; `requiredNeighbors` requires each listed kind beside the target, without consuming it or requiring a weld. Conditions observe pre-cooking geometry, so diagonal and row-wrapped cells do not count. Paused progress persists even if neighbors are absent on save/load. Optional `weldTo` kinds select orthogonal neighbors before cooking, and eligible welds commit after all transformations, before motion. Glassmaking joins existing glass only: simultaneously cooked sand does not join, and later ticks do not add welds. |
| Grinders | Transform front stone or glass into sand in four active ticks, preserving target identity but removing its welds because sand is unweldable. Share furnace side-disable/rear-active ports, target-ID progress, movement/cloning/duplication, and nested-board processing. `processingRecipeFor(machine, input)` in `furnace.ts` selects distinct furnace/grinder tables. Both use the existing furnace runtime buffers and scene `furnaces` progress field; loading validates the recipe against the actual machine kind. |
| Delivery boxes | Compare complete front/rear bodies under translation only: kinds, directional orientations, handedness, and weld topology, not configuration. Atomically consume the front match and pulse sideways. Competing claims jam. |
| Body comparers | Use delivery-box translation-only matching on complete front/rear bodies without consuming either. Drive +1 continuously on the shared side network while matched, otherwise 0. Missing neighbors or bodies welded to the comparer do not match. Observe start-of-tick geometry, including inside rune arrays. |
| Block type comparers | Compare only the kinds of the immediate front/rear blocks, ignoring orientation, configuration, welds, and surrounding bodies. Both cells must be occupied; empty cells or board edges do not match. Blocks welded to the comparer are allowed. Drive +1 continuously on the shared side network while matched, otherwise 0, without consuming anything. Observe start-of-tick geometry, including inside rune arrays. |
| Duplicators | Prior positive shared-side charge mirrors the rear body onto the pointed side. All destinations must be empty/in bounds; overlapping output intents jam. Copies get fresh IDs, reflected orientations/handedness/welds, transformed runtime configuration, and remapped internal furnace target IDs. |
| Assemblers | Match the complete front body against precomputed recipe rotations, ignoring internal configuration. Consume atomically, queue rotated outputs, then emit one unwelded fresh-ID tile per tick behind while space is empty. Previous-tick local-left -1 pauses both consumption and emission without losing queued products; 0/+1 enables. The isolated local-right output pulses +1 on emission only, reaching connected circuits in that same tick. Pending queues block new consumption. Body/output claims jam; collection excludes assemblers claimed by delivery and output cells claimed by accepted duplication before circuits resolve, while commit still rechecks changed bodies/destinations. Recipes and variants live in `assembler.ts`; queues and separate control/output charges follow transforms and persistence. |
| Drills | Destroy the immediate front tile and its welds after four active ticks, not its whole body. Previous-tick shared side -1 pauses progress; 0/+1 enables. The isolated rear output is +1 on each active tick, including completion, and 0 while paused, jammed, or without a destructible target. Progress follows stable target IDs and resets on target changes; it reuses furnace cell storage and scene `furnaces` state for movement, cloning, transforms, duplication, and save/load. Collect targets before circuits, then commit after production/consumption and before motion, skipping removed/replaced targets. Multiple active drills claiming one tile jam and pause progress; mutually facing drills can finish simultaneously. Newly produced drills retain their copied state without acting until the next tick. Front welds are forbidden. The `indestructible` flag protects platforms on observation and commit, but not from editor deletion or delivery consumption. |

Dedicated `*-resolver.ts` files own machine intent collection and commits. `MotionWorkspace` shares conveyor/thruster force collection and dependency/conflict resolution; reuse that machinery rather than introducing order-dependent pushing.

`TileDefinition.runtimeWeldProtected` marks platforms, indestructible channels, and delivery boxes. Welders, splitters, and laser splitters cannot create or remove an edge when both endpoints carry this flag; an edge with only one protected endpoint remains eligible. Rejected edges produce no change pulse, and laser beams continue past them. This restriction lives in the machine resolver, not `World.canWeld`/`setWeld`, so manual sandbox/solution editing remains unrestricted by the flag. Protection is tile-kind metadata, independent of destruction immunity, with no serialized state.

An empty rotator grip turns without anchoring its base or competing with body turns. Commit these grip-only direction changes before accepted cell rotations, so a carrier transforms the updated direction along with the carried rotator's orientation. Nonempty competing turns still jam.

Mirrored assemblers swap control/output sides and match a separately precomputed reflected recipe set. Recipe geometry, weld ownership, component handedness, and product orientations reflect before rotation. Pending outputs retain their own handedness through subsequent machine transforms and emission.

Before gravity, `MotionWorkspace` probes powered sources and their contact chains through the shared driven resolver, using the summed machinery forces on each source body. Reserved chains hold against gravity even when jammed; successful destinations also exclude falling bodies. Magnetic gravity groups containing reserved bodies remain supported, then ordinary welded axes are restored for the final driven solve. Conveyor-only bodies retain the old gravity-first rules. Reservation scratch allocates only when thrusters or projected commands occur, remains cached, and is cleared when power disappears. No geometry commits during reservation, and force sums are reused rather than observed twice.

Powered reservation allocates its gravity-root backup only when magnetic contacts require temporarily switching from gravity groups to welded drive bodies. Contact-free powered ticks neither allocate nor access that backup. Once allocated, it remains cached across contact removal/reset and is refreshed before every magnetic reservation probe.

Probe each requested force axis against boundaries, slider restrictions, and braced push chains (including magnetic normal coupling). Discard geometrically blocked axes before proposing driven movement: blocked lift must not cancel sideways travel along a ceiling, and a downward belt force braced by the floor must not prevent a stone from being pushed sideways. These probes ignore other driving intents; the ordinary dependency and destination resolver still jams competing viable movements. The pre-gravity reservation pass retains jammed single-axis powered chains so they continue holding against weight; two-axis reservations still discard blocked axes. Probes reuse gravity scratch storage and do not allocate per tick.

`PistonResolver` resolves one-cell strokes in dependency-ordered rounds within the piston phase. A proposal that carries another piston with a viable pending stroke waits for that piston; a blocked piston can instead be carried rigidly. Towers therefore stroke from the distal end toward the driving base, for both extension and retraction. Each round rebuilds proposals against committed geometry, so a barrier permits as many strokes as fit rather than rejecting the entire tower. Blocked/deferred strokes retry after progress. A successful stroke changes kind while retaining the tick's charge, preventing a second stroke by that piston. Circuits, gravity, and rotators do not rerun.

Each proposal splits only its acting head connection, with an exception for aligned actuators welded to the same load: their matching head strokes form a required acceptance bundle. Other pistons remain rigid, including already-completed and inactive ones. Extension tries forward pushing first, then recoil if geometry blocks that individual forward proposal; competing otherwise-feasible forward strokes jam instead of switching to recoil. Retraction pulls only weld closure, never an unwelded obstruction.

Ready proposals resolve together. Compatible translations merge; opposing/perpendicular swept motion and distinct final occupants (including new arms) jam every rival. Every eligible member still claims its path after discovering a conflict. A stationary shared base does not couple independent heads. If an ordinary round makes no progress, an iterative strongly connected component pass identifies circular carrying dependencies (including required shared-load partners). Within a cycle only, vertical strokes may carry pending horizontal pistons without waiting for them. Acyclic dependencies, same-axis dependencies, and required partner readiness remain binding; all ready proposals still undergo ordinary collision resolution. After progress, normal dependency ordering resumes against the new geometry. Unresolved cycles still jam; general expanding piston rings are not solved. Priorities depend on mechanical dependencies and this vertical-first cycle rule, never tile IDs or scan order.

Commit removes accepted kinematic weld seams before cell copying and restores them through piston transitions. Moved fasteners remain solid through that round's transition, then break before the next round. Stable arm identities and all non-head welds/state survive carrying; rendering interpolates the original and final tick snapshots, including board-spanning net travel, not individual substeps.

`rotation-animation.ts` retains render-only accepted-turn records outside `World` state, keyed by carried stable tile IDs. `Simulation.step(previousWorld)` enables capture for matching root/nested snapshots and seals it after all commits, including production updates to the interpolation source. Subsequent ticks, edits, and reset invalidate the records; cloning and serialization never copy them. This does not alter rotator collision resolution or phase ordering.

Raw materials include dirt, gold, silver, ruby, sapphire, emerald, diamond, amethyst, mithril, copper ore, copper, and wood. These use ordinary weldable, gravity-affected solid-block physics without magnetic or circuit behavior. Copper ore smelting requires adjacent wood; the existing sand/glass and iron recipes are unchanged.

## Circuits and configurable state

`circuit-resolver.ts` resolves signed-ternary (-1, 0, +1) driver sums by sign. Cached welded-network union topology spans all nested boards and invalidates when geometry or the tree changes. Compact nodes cover circuit cells, with a lazy cell-to-node lookup. Worlds without circuit cells, including empty inner arrays, skip charge commits and allocate neither circuit output buffers nor node lookups. Previously allocated lookups remain cached after circuit removal, with stale node numbers cleared on topology rebuild.

* Conduits share one network; crossings isolate horizontal/vertical axes. Mechanical weld eligibility and circuit connectivity are distinct.
* Indestructible channels (board code `{`, Puzzle Tools palette) share all four ports like ordinary channels, but drills cannot destroy them or sever their welds by drilling. They remain gravity-affected and movable; weld them to platforms when protected puzzle wiring must stay fixed. They require no component state and use ordinary scene/puzzle serialization.
* Fixed charge drives +1 every tick; spark only on the first tick. Occupancy sensors inspect exactly one forward cell and ignore kinds marked `invisibleToSensor` (glass), without seeing through them. Charge sensors scan forward through empty cells and those invisible kinds, reading the first detectable tile's start-of-tick near-side port charge. Other occupied tiles block the scan; non-circuit tiles and an empty ray to the root boundary read neutral. Sensors permit front mechanical welds but no front circuit link, and drive their other three isolated outputs.
* Movement sensors have four isolated outputs: +1 toward the previous tick's net cell displacement, -1 opposite, and 0 on unchanged axes. Diagonal motion activates both axes; motion that returns to its starting cell reports zero. `movement-sensor.ts` captures stable-ID positions before circuits and records displacement after all ordinary/rotator/piston phases. Newly placed sensors start neutral; newly duplicated sensors do not replay pending template motion. Inner boards measure local motion, not movement of their containing arrays; outputs can drive virtual array ports.
* Sparse `movement-sensor` state separates pending signed `motionX`/`motionY` from committed `ports`. Cloning/reset and scene persistence preserve both; flips/turns transform the vector and side ports. All-zero scene state is omitted. Simulation scratch is lazy per world, and geometry observation never depends on rendering or interpolation snapshots.
* Directional gates isolate inputs from outputs. Inverter, combiner, rectifier, subtractor, selector, multiplier, equality, minimum, and maximum use metadata-defined ports. Multiplier/equality/minimum/maximum ignore disconnected inputs; empty-input identities are +1/+1/+1/-1. Connected neutral input is not disconnection.
* Delay gates copy only the previous-tick rear input to the isolated front output, including negative and neutral charges; disconnected rear inputs produce 0. Side welds are mechanical only. They have no configurable queue or sparse state, unlike Delay Runes, and use ordinary directional transforms and charge persistence. Their distinct kind (board code `;`) permits independent puzzle availability/pricing.
* `World.chargeAtPortIndex` reads charge exposed to neighbors: isolated input/sensing ports return neutral, never the tile's stored output. A direct input-to-input weld is connected but undriven, so it contributes 0 rather than a disconnected-input identity. Render input traces from the neighbor's facing port and gate glyphs from the gate's stored output.
* Delays advance a configurable ternary ring buffer. Counters accumulate signed input modulo a threshold, pulsing in the wrap direction. ROM left/rear inputs move a 2D cursor, local-left input before rear input; crossing an edge carries into the other dimension in the component's frame. Independent spatial `wrapX`/`wrapY` flags default to true, including when omitted from scene JSON. Each move is ignored if its direct step or carry would wrap across a disabled axis; the other input still runs. Changed grid or wrapping settings clear the cursor/output, while unchanged configuration preserves progress. Front/local-right outputs drive the selected value.
* Lookup runes use a fixed 3×3 ternary truth table: local-left input selects the column, rear input selects the row, both ordered -1, 0, +1. Front/right outputs emit the selected value using ordinary previous-tick gate timing; disconnected inputs select 0. Sparse `lut` state stores nine values and fixed dimensions, never a cursor. Tables retain their logical input mapping through rotations/reflections, unlike spatial ROM grids. Changed configuration clears output; identical configuration is a no-op. Scene import validates the exact dimensions and ternary values; movement, cloning, duplication, and nested boards preserve them. Lore graphers do not display lookup tables.
* Discard runes suppress their first N rear-input ticks (including zero/disconnected input), then drive the front output from the old rear charge on every subsequent tick. E configures N from 0 to 99, default 3; zero passes immediately with ordinary gate timing. Sparse `discard` state holds `length` and saturated `discarded` progress; changed configuration clears progress/output, while unchanged configuration is a no-op. Movement, cloning, transforms, duplication, and nested scene persistence preserve progress.
* ROM transforms rotate/reflect the stored grid in board coordinates (flips before clockwise turns), swap rectangular dimensions and wrapping flags on quarter-turns, and move the live cursor with its selected cell. Reflections preserve wrapping flags and swap port handedness. Cursor deltas follow the physical input directions; carry directions and input priority follow the component frame, not world-horizontal-first ordering. `World.advanceRomAtIndex` accepts spatial deltas, resolves movement in the local frame without allocating, then maps the cursor back to spatial storage. This applies to selections, board/nested-array transforms, rotators, and duplicator copies. Lookup tables retain logical addressing; sequence checker grids retain their time-ordered sequence rather than transforming spatially. Gravity remains world-down, outside component-local symmetry.
* Sequence checkers ignore rear input until its first nonzero value, then compare one row-major expected value per tick. Optional `ignoreZeros` mode waits through every neutral input and checks only the order of +1/-1 values; its expected grid must contain no zeros. They latch failure at the mismatched cursor or success past the final value. Changing either the grid or mode rewinds cursor/verdict. The mode follows cloning/transforms and scene persistence; an omitted JSON flag means false.
* Victory inputs latch root win/loss from positive/negative charges; opposing same-tick intents jam. Monitors merely join circuits; history and checker start ticks are display state, not serialized simulation state.

`configurable-components.ts` owns configuration definitions, validation, defaults, snapshots, cloning, and rotation/flip transforms. Sparse runtime state is broader than player-editable configuration (e.g. assembler queues, rotator grips).

Monitors and graphers retain a display-only signed safe-integer `order`, default zero. Snapshot/clone/transform paths preserve it; scene JSON omits zero and validates nonzero values on import. Signal-panel dragging is its only editing UI. Puzzle solution transfer may copy this presentation field onto matching fixed components, including nested arrays, without copying their simulation configuration.

## Nested rune arrays

`rune-array.ts` defines odd inner dimensions from 1x1 to 15x15 (default 5x5), centered resizing, ports, and nesting rules. Each array owns a full inner `World`; arrays nest recursively, with every ordinary phase active inside.

The four inner edge-center cells connect as if a conduit sat just beyond each edge. Four independent outer side networks join the forest-wide circuit solve without extra delay. Inner victory latches the root result; nested boards have no separate result.

Charge-sensor rays reaching an inner edge-center port continue from the containing array's cell into its parent board, without requiring an external weld. Empty gaps and invisible tiles (glass) are skipped inside and outside arrays; traversal can continue through multiple enclosing edge-center ports. Other wall cells and the root boundary read neutral. An occupied array encountered from outside is itself the sensed tile: its facing-port charge is read, not its contents. This does not electrically join the sensor's front to the array port or change ordinary gates' virtual-port inputs.

Rotation/reflection transforms the inner board physically, keeping its gravity downward. Copies/resets reuse an existing inner world with matching tile ID and dimensions, preserving mounted views and resolver caches. In puzzles inner components cost their full catalog prices; the containing array occupies one footprint cell.

## Adding or changing components

Start with `tile.ts`: the registry supplies behavior, board codes, directionality, palette grouping, descriptions, and suggested prices. Then inspect the relevant resolver and its tests. Stateful additions also need configuration/snapshot/transform handling, feature indexing, and board serialization; visual and editable additions need the shared renderer and configuration workflow, respectively. Do not invent a parallel metadata registry.

Check movement, cloning/reset, rotations/reflections, duplication, and nested boards for new state. Preserve stable IDs during movement and allocate fresh IDs only for genuinely new tiles. Feature indices and revisions must remain correct through every mutation path.

## Serialization and verification

`board-export.ts` owns deterministic versioned scene JSON: explicit bounded dimensions (1x1 through 400x300), compact ASCII kind/weld grids, sparse orientation/handedness/charge/runtime state, and recursive array contents. Optional `mirrored` lists `{x, y}` entries only for mirrored asymmetric tiles; duplicates, out-of-bounds entries, and symmetric targets are rejected. Assembler pending outputs optionally carry `mirrored: true`. Weld codes are `.`, `-`, `|`, `+`. Optional empty sparse fields are omitted and import as empty. Runtime IDs are deliberately excluded and reconstructed on import.

Validate the complete board and sparse state before replacing a live world. Nested contents use the same board fields without top-level format/version/tick/result; nesting is bounded to eight levels. Puzzle wrappers/catalogs/case overrides are covered in [UI/lifecycle](ui-lifecycle.md).

Focused regressions live in `tests/` by subsystem: `simulation`, `circuit`, `conveyor`, `piston`, `rotator`, `weld-operation`, `furnace`, `delivery`, `duplicator`, `assembler`, `checker`, `rune-array`, `world-features`, and `board-export`. Exercise observable behavior, conflict/boundary cases, and state preservation rather than duplicating the implementation. `tools/ternary_logic_search.py` explores minimum-size combinational ternary circuits independently of physical layout.
